## Successes

### 1. Spec-First Approach Paid Off Massively

The protocol spec (`docs/protocol.md`) from Epic 19 was the implementation blueprint. Having the full wire format designed and reviewed before writing any server/SDK code meant the team could focus on correctness rather than design debates. The 7.4x throughput improvement validates the decision to build a custom protocol rather than staying on gRPC.

### 2. Biggest Performance Win in Project History

7.4x enqueue throughput, 4.5x p99 latency reduction. This is not incremental — it's a generational improvement. The binary protocol eliminated HTTP/2 framing overhead, protobuf serialization on the hot path, and gRPC's connection management complexity. Combined with Epic 18's tracing fix (+20.7%) and Epic 19's batch-native scheduler, Fila's performance story is now compelling.

### 3. Clean Removal of Legacy Transport

Net -3,400 lines after removing gRPC. The codebase is simpler, has fewer dependencies (no tonic/prost on the server hot path), and has a single transport to maintain. The phased approach (stories 20.1-20.4 built binary, 20.5 removed gRPC) was methodical and safe.

### 4. SDK Delivery Pipeline Architecture

The two-stage delivery pipeline (TCP → Reader → unbounded internal → Forwarder → bounded user channel) with application-level backpressure is a well-designed solution. Backpressure via atomic counter + high-water mark prevents memory exhaustion without deadlocking the response path. Proven by test with 10K messages.

### 5. Comprehensive Review Process

The epic-review caught critical bugs that would have been shipped: ConsumeOk missing opcode, u16 truncation across 7 sites, cluster admin handlers bypassing Raft, SDK delivery channel deadlock, multiple lifecycle bugs. The 4-day review was the longest in project history but also the most productive — this was the most complex epic to date.

## Challenges

### 1. Protocol Implementation Gaps Despite Spec

Despite having a detailed protocol spec, the implementation missed key elements:
- **ConsumeOk opcode absent** — consume hung forever waiting for a response that didn't exist. The spec defined the opcode but the server never sent it.
- **Continuation frame reassembly specced but not implemented** — ContinuationAssembler had to be added during review.
- **u16 list count truncation** — 7 encode sites would silently corrupt frames with lists >65,535 items.

**Root cause:** The spec was treated as a reference, not as a checklist. When implementing, the developer went function-by-function through the gRPC handlers rather than opcode-by-opcode through the spec.

### 2. Async Lifecycle Bugs in SDK (Systematic Pattern)

The SDK had **5 distinct lifecycle/cleanup bugs**, all variations of the same pattern — async tasks and channels not properly managed on Drop/disconnect:
- Background reader task leaked on client drop (no CancellationToken)
- Dropping consume stream didn't send CancelConsume
- Delivery channel deadlock (bounded send blocked reader, starving responses)
- Delivery channel registered too late (race with early deliveries)
- redirect_consume dropped temporary client, killing background reader

**Root cause:** Async Rust resource cleanup is hard. Drop is synchronous but cleanup needs async. The developer implemented the happy path first without designing the cleanup path. Each bug was discovered independently during review rather than being caught by a systematic lifecycle review.

### 3. Repeated Reviewer Feedback (Stream Enum)

The Stream enum used manual method delegation in 3 places (server, SDK, CLI). The reviewer gave the same feedback — "implement AsyncRead/AsyncWrite traits instead" — **three separate times** before it was fully addressed.

**Root cause:** The developer fixed each instance locally when flagged rather than searching for the pattern across the codebase. Review feedback should trigger a grep for the same pattern, not just a point fix.

### 4. Test Infrastructure Fragility

Multiple test infrastructure issues surfaced repeatedly:
- **Stdout pipe not drained** — server blocked on full pipe buffer, causing TLS e2e tests to hang. Fixed in 5 places.
- **free_port() returning duplicate ports** — dedup loop added in 4 places.
- **CLI tests using wrong address** — still pointed at gRPC address after migration.

**Root cause:** Test infrastructure evolved organically over 20 epics without a unified test helper abstraction. Each test suite has its own server start/port allocation/address logic.

### 5. CryptoProvider Dual-Provider Panic

Adding tokio-rustls alongside tonic's tls-ring caused a runtime panic from conflicting rustls CryptoProvider installations. This is a known rustls footgun but wasn't caught until integration tests ran.

**Root cause:** Dependency-level conflicts are invisible at compile time. This class of bug requires integration testing to surface.

## Key Insights

1. **Spec-as-checklist, not spec-as-reference** — When implementing a protocol from a spec, walk the spec opcode-by-opcode and tick them off. Don't translate from the old implementation; implement from the spec.

2. **Async lifecycle design must be explicit** — For any struct that spawns background tasks or holds channels, design the cleanup/drop path *before* implementing the happy path. Document it in a comment: "On drop: cancel reader, send CancelConsume, drop channels."

3. **Review feedback = grep for pattern** — When a reviewer flags a pattern issue (not just a point bug), the fix should include a codebase-wide search for the same pattern. Don't wait for the reviewer to find the other instances.

4. **4-day review was worth it** — The review caught ConsumeOk (would have shipped a broken consume), u16 truncation (silent data corruption), cluster bypass (split-brain risk), and SDK deadlock (production hang). Every day of review prevented a class of production bug.

5. **Performance validates architecture** — 7.4x is not optimization — it's the payoff from a correct architectural decision (custom binary protocol vs gRPC for a message queue). Spec-first (19) → implement (20) → measure was the right sequence.
